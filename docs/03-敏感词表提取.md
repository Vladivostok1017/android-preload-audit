# 十五、敏感词表提取进展

## 15.1 已取得的部分

| 产物 | 位置 | 大小 |
|---|---|---|
| 词表原始文件 | `securitycenter-dict\dict.bin` | 3,639,702 字节 |
| 词表加载库（arm64） | `securitycenter-dict\liblib-riskcontrol.so` | 247,832 字节 |
| 词表加载库（armv7） | APK 内 `lib/armeabi-v7a/liblib-riskcontrol.so` | 132,700 字节 |

APK 内 `assets/` 共 234 个条目，唯一相关文件为 `assets/dict`。

## 15.2 格式判定

`dict.bin` 前 64 字节：

```
00 00 00 01 00 00 00 00 bf d0 cf db 7d b6 af 6d d4 cc b6 3b 5c 48 47 65
d4 cc b6 3b 5c 48 47 65 bf f7 71 b7 f8 cb 31 d5 d4 cc b6 3b 5c 48 47 65
```

- 熵 = **6.102 bit/byte**，属压缩或加密数据，非纯文本、非随机
- UTF-8 中文片段 0 处；GBK、UTF-16LE 解码均为乱码
- 前 8 字节 `00 00 00 01 00 00 00 00` 疑似版本号 + 保留位

## 15.3 解密链路（由未 strip 的符号还原）

`liblib-riskcontrol.so` 保留了完整的 C++ 符号，调用链清晰：

```
SensitiveWordDetectCore::readFileFromAsset()     // 读 assets/dict
SensitiveWordDetectCore::decryptFromFile(char*, size_t)
AES::KeyExpansion(const unsigned char*, unsigned char*)
AES::DecryptCBC / DecryptECB / DecryptCFB        // 三种模式均有实现
SensitiveWordDetectCore::censor(std::string const&)
SensitiveWordDetector::load(char*) / censor(...)
```

对应 Java 侧 `com.miui.riskcontrol.SensitiveWordDetectProvider.hasSensitiveWords(String)` **无 Java 实现体**，为 JNI 调用。

结论：词表经 AES 加密存放，运行时解密后加载进内存，匹配在 native 层完成。

## 15.4 当前受阻原因

| 尝试 | 结果 |
|---|---|
| 直接读 `assets/dict` | 加密，无明文 |
| 本机 Ghidra 反汇编 `liblib-riskcontrol.so` | 失败：Windows 上 Ghidra 只接受 PE，拒绝 ELF/arm64 |
| Hopper | 失败：仅支持 macOS |
| IDA | 未配置 |
| 用 .so 内字符串做 AES 密钥爆破（725 个候选 × 多尺寸 × 多偏移 × ECB/CBC） | 唯一"命中"经核验为随机字节假阳性，输出为乱码 |

## 15.5 可行路径

| 路径 | 可行性 | 说明 |
|---|---|---|
| 动态内存提取 | 高 | 恢复 `com.miui.securitycenter`，触发 Provider 加载词表，从 `/proc/<pid>/mem` dump 进程内存，按中文正则提取。需要 root 与解密后的内存镜像 |
| 换平台静态分析 | 高 | 在 Linux/macOS 上用 Ghidra 或 IDA 分析 `liblib-riskcontrol.so`，定位 `decryptFromFile` 中 `KeyExpansion` 的密钥来源 |
| 换反汇编器 | 中 | 本机若配置 IDA（`REA_IDA_MCP_CONFIG`）可直接分析 arm64 ELF |
| 黑盒探测 | 低 | 通过 Provider 尝试候选词判断命中，但只能验证不能穷举 |

无论走哪条路，**词表本身不含上传通道**，提取的价值在于确认哪些词被判定为敏感（属能力透明度问题），不影响前文关于「检测在本地完成」的结论。

## 15.6 动态提取实测（设备 B，已执行并回滚）

### 执行过程

1. 恢复 `com.miui.securitycenter`（`install-existing`，不清数据）→ 成功
2. 启动应用主界面，确认进程与 Provider 注册状态
3. 以 root、system(1000)、shell 三种身份调用 `content call`
4. 核对本机安全中心版本与组件构成
5. 重新卸载，清理进程，复查状态

### 结果：本机无法完成提取

| 检查项 | 实测结果 |
|---|---|
| 本机版本 | `6.2.0-220418.0.2`（MIUI 13，`/system/priv-app/SecurityCenter`） |
| 设备 A 版本 | `12.8.7-260927.0.1`（HyperOS，`/data/app` 更新版） |
| `com.miui.riskcontrol` Provider 注册数 | **0** |
| `content call` 三种身份 | 均返回 `Could not find provider: com.miui.riskcontrol` |
| 本机 APK 内 `assets/dict` | **存在**，3,639,702 字节 |
| 本机 APK 内 `liblib-riskcontrol.so` | **不存在** |
| 本机 dex/manifest 中 `riskcontrol`、`SensitiveWord` 出现次数 | **均为 0** |
| 本机是否有 dex/so 引用 `assets/dict` | **无任何引用** |

结论：设备 B 的 MIUI 13 版本**没有实现该功能**，`assets/dict` 是一份随包下发但无人引用的死文件。该设备上无法触发解密，内存提取无从下手。

### 附带结论：词表跨版本字节一致

```
设备 B v6.2.0  assets/dict  SHA-256: f99086243babe60fd6d50f8d06bfdd15cefcbf0dc867b0e10521c2f6559cc668
设备 A v12.8.7  assets/dict  SHA-256: f99086243babe60fd6d50f8d06bfdd15cefcbf0dc867b0e10521c2f6559cc668
```

两个相差数个大版本的 ROM，词表**完全一致**。这说明该词表长期未更新，也说明它是平台层统一投放的静态资源，而非随安全中心迭代维护。

### Provider 的调用约束（由反编译得知）

```java
public final Bundle call(String str, String str2, Bundle bundle) {
    Log.i("SWDP", "call method = " + str + " arg = " + str2);
    if (!f33674a.contains(getCallingPackage())) {          // 包名白名单
        Log.i("SWDP", getCallingPackage() + "not in whiteList!");
        return null;
    }
    if (!"METHOD_SENSITIVE_WORD_DETECT".equals(str)) return null;
    setAssetManager(getContext().getAssets());
    Bundle b = new Bundle();
    b.putBoolean("hasSensitiveWords", hasSensitiveWords(str2));
    return b;
}
```

- 方法名固定为 `METHOD_SENSITIVE_WORD_DETECT`，参数为待检测文本，返回 `hasSensitiveWords` 布尔值
- **调用方必须在白名单内**，非白名单包直接返回 null，因此 shell 与 root 身份都无法调用
- 白名单字段 `f33674a` 在构造器中初始化，该构造器无法被 jadx 还原（`no decompiled body`），白名单具体内容未取得
- `hasSensitiveWords(String)` 同样无 Java 实现体，确认为 native

### 下一步的必要条件

动态提取只能在设备 A（HyperOS，含 riskcontrol 组件）上执行，且需先解决白名单限制：以白名单内包的 uid 调用，或直接在进程内存中定位已解密的词表。设备 A 当前未连接。

### 现场状态

```
com.miui.securitycenter → 已卸载（-u 可见，数据保留）
相关进程               → 0
```

操作仅为 `install-existing` 与 `uninstall -k`，未修改分区、未写入 boot 脚本。

## 15.7 设备 A 实测（K80 / HyperOS，已执行并回滚）

### 白名单已解出

`<clinit>` 反编译结果：

```java
static {
    Uri.withAppendedPath(Uri.parse("content://com.miui.riskcontrol"), "censorResult");
    ArrayList<String> arrayList = new ArrayList<>();
    f33674a = arrayList;
    System.loadLibrary("lib-riskcontrol");
    arrayList.add("com.android.camera");
    arrayList.add("com.miui.mediaeditor");
}
```

白名单**只有两个包**：

```
com.android.camera        （相机，uid 10141）
com.miui.mediaeditor      （相册编辑，uid 10286）
```

同时确认：类加载时即 `System.loadLibrary("lib-riskcontrol")`，另存在 `content://com.miui.riskcontrol/censorResult` 路径。

**功能面由此收窄**：该敏感词检测实际服务于**相机与相册编辑**，与其在系统设置、短信、输入法中的通用内容过滤无关。

### 调用尝试与结果

| 身份 | 结果 | 原因 |
|---|---|---|
| root（uid 0） | `Result: null` | 有 provider 外部访问权限，但 callingPackage 非白名单，`call()` 返回 null |
| securitycenter 自身 uid（本机为 1000，system） | `NullPointerException` | callingPackage 解析异常 |
| `com.android.camera` uid 10141 | `SecurityException` | 缺 `android.permission.ACCESS_CONTENT_PROVIDERS_EXTERNALLY` |
| `com.miui.mediaeditor` uid 10286 | `SecurityException` | 同上 |

两道校验互斥：**有外部访问权限的身份（root/shell）过不了包名白名单；命中白名单的身份（相机/相册编辑）没有外部访问权限**。因此用 `content` 命令行无法完成触发。

### 结论

词表的用途与调用方已完全确认（见上），但解密后的明文仍未取得。剩余可行手段：

| 手段 | 前提 |
|---|---|
| Frida 附加 securitycenter，直接读取 `f33674a` 与 native 层解密结果 | 需在设备上部署 frida-server |
| 自建 dex 以相机 uid 运行并持有外部 provider 权限 | 需 dex 构建工具链（本机执行 java/d8 被环境拒绝） |
| 触发相机的内容合规检测路径 | 需确认相机内哪个功能会调用 `censorResult` |
| 换平台静态分析 `liblib-riskcontrol.so` | 需 Linux/macOS 的 Ghidra 或 IDA |

## 15.9 静态反汇编进展（capstone）

Java 桥不可用后，改用本机 capstone 直接反汇编 `liblib-riskcontrol.so`（arm64）。

### 已确认的结构

| 位置 | 内容 |
|---|---|
| `decryptFromFile` @0x150cc，size 180 | 先取块大小算余数，余数非 0 则打印 `needPadding %u char(s)` 并补齐；随后调用 `bl 0x10080`（PLT） |
| 调用参数 | `x0 = sp+8`（AES 对象）、`x1 = 数据指针`、`w2 = 长度`、`x3 = 0x3d008`、`x4 = 0x2fb64` |
| `AES::AES(AESKeyLength)` @0x10648 | 仅设置 `Nk`/`Nr` 与块大小 `0x10`，不写入密钥 → 密钥由调用方传入 |
| `.data` @0x3d008 | **32 字节高熵常量**：`892ef43c669d88e491b511e0587c414a25688788e9149ee220654914a1b8b173`，即密钥候选 |
| `.rodata` @0x2fb64 | `52 09 6a d5 30 36 a5 38 bf 40 a3 9e 81 f3 d7 fb ...`，为 **AES 逆 S-box 表**，非 IV |
| 明文格式线索 | 字符串 `load file!`、`File has %d lines`、`Load file tree fail!!!`、`censor sentence %s`、`/storage/emulated/0/censor_source` |

由字符串可确认：解密后是**逐行文本**（每行一个词），由 `SensitiveWordDetector::load` 读入并构建树（trie）。

### 解密尝试结果

用上述 32 字节密钥，对 `dict.bin` 测试 AES-128/256、ECB/CBC/CFB/OFB/CTR、5 种偏移（0/4/8/16/24）与 5 种 IV 组合，共上百种组合：

- 无任何组合产出可读中文
- 最高"中文计数"仅 35（1.6 万字节样本中的随机字节巧合）

结论：该库的 AES 为**自带实现**（`AES::SubBytes`/`MixColumns`/`KeyExpansion`/`Rcon` 全为自写），其轮数、字节序或 S-box 使用方式与标准库实现存在差异；或密文之外还有一层处理。标准 AES 库无法直接还原。

### 到这一步的净收获

| 已确定 | 未确定 |
|---|---|
| 词表是逐行文本、构建为 trie | 具体词条内容 |
| 加密为 AES 类算法，密文 3.64 MB | 该实现的准确参数 |
| 密钥候选位于 `.data:0x3d008`（32 字节） | 密钥是否经二次派生 |
